# ChatSphere Software Requirements Specification

## 1. Introduction

### 1.1 Purpose
ChatSphere is a web-based real-time messaging application. It allows users to create an account with email verification, complete a profile, search registered users, send private messages, manage saved/self messages, and use an admin panel for user moderation.

### 1.2 Scope
The system is designed as a production-style chat website deployed online. The frontend is hosted on Netlify, the backend API is hosted on Railway, and user/message data is stored in an online Supabase PostgreSQL database.

### 1.3 Intended Users
- Normal users who create accounts and send private messages.
- Admin user who can view, block, unblock, and delete users.

## 2. Technology Stack

### 2.1 Frontend
- Framework: Next.js 14
- Language: TypeScript
- UI Library: React
- Styling: Tailwind CSS
- Icons: Lucide React
- Emoji Picker: `emoji-picker-react`
- Hosting: Netlify

### 2.2 Backend
- Language: Go
- Web Framework: Gin
- Realtime Layer: WebSocket using Gorilla WebSocket
- Password Hashing: bcrypt
- Auth Session: Signed bearer token generated by backend
- Hosting: Railway

### 2.3 Database and Services
- Database: Supabase PostgreSQL
- Connection: Supabase Transaction Pooler through Railway `DATABASE_URL`
- Email OTP Service: Brevo SMTP/API
- Version Control: GitHub

## 3. System Features

### 3.1 User Registration
Users can create an account using:
- First name
- Optional last name
- Email address
- Password

After signup, the system sends a 6-digit OTP code to the user's email. The user must verify this code before continuing.

### 3.2 Login
Users can login using email and password. On successful login, the backend returns a signed private token used for protected API calls.

### 3.3 Forgot Password
Users can request a password reset from the login screen. The system sends an OTP code to email. After verifying the code, the user can set a new password.

### 3.4 Profile Management
After account creation, users complete their profile. Users can later update:
- First name
- Last name
- Profile picture

Profile updates are saved through the backend to the online database.

### 3.5 User Search and Contacts
Logged-in users can search registered users by name or email. Search results show user name, avatar/initials, and online/offline status.

### 3.6 Private Messaging
Users can send messages to another registered user. Messages are stored in the database and shown in the Inbox section for both sender and receiver.

Privacy rule:
- Ali sending Hamza a message is visible only in Ali-Hamza conversation.
- Mohsan opening Hamza chat sees only Mohsan-Hamza messages, not Ali-Hamza messages.

### 3.7 Realtime Delivery
When a message is saved, the backend broadcasts it through WebSocket only to the sender and receiver. Browser clients are receive-only for realtime messages; message sending must go through the protected HTTP API.

### 3.8 Self Chat / Saved Messages
When a user searches their own account, it appears as a self-chat entry. The user can open it like a normal chat to save personal messages.

### 3.9 Attachments and Emojis
The chat input supports:
- Emoji picker
- File picker for images, videos, documents, archives, and APK files
- Attachment preview before sending

### 3.10 Admin Panel

Admin can:
- View all users
- Delete users
- Block users
- Unblock users

## 4. Functional Requirements

### 4.1 Authentication Requirements
- The system shall require OTP verification during signup.
- The system shall hash passwords before storage.
- The system shall issue a signed bearer token after login/profile completion.
- The system shall reject protected requests without a valid token.
- The system shall reject invalid email/password login attempts.

### 4.2 Messaging Requirements
- The system shall save each message in the database.
- The system shall load inbox messages only for the logged-in user.
- The system shall load a chat conversation only between the logged-in user and selected user.
- The system shall prevent one user from reading another two users' conversation.
- The system shall broadcast realtime messages only to sender and receiver.

### 4.3 Profile Requirements
- First name is required.
- Last name is optional.
- Profile picture is optional.
- If no profile picture exists, the UI shall show initials.

### 4.4 Admin Requirements
- Admin login shall be separate from normal user login.
- Admin-only endpoints shall require the admin token.
- Admin shall be able to delete/block/unblock users.

## 5. Non-Functional Requirements

### 5.1 Security
- Passwords must be stored using bcrypt hashes.
- Private message APIs must require signed tokens.
- The frontend must not decide privacy rules by itself; backend enforces access.
- OTP codes expire after 10 minutes.

### 5.2 Performance
- The UI should load quickly through static Netlify hosting.
- Backend API should respond quickly through Railway.
- Database queries should use conversation id and created time indexes.

### 5.3 Availability
- Frontend is publicly available through Netlify.
- Backend is publicly available through Railway.
- Database is hosted by Supabase.

### 5.4 Usability
- The interface should be responsive for desktop and mobile.
- Mobile should show inbox/search first, then open chat after selecting a user.
- Chat search should stay within screen boundaries.

## 6. Architecture

### 6.1 High-Level Flow
1. User signs up in frontend.
2. Backend sends OTP through Brevo.
3. User verifies OTP.
4. User completes profile.
5. Backend stores user in Supabase PostgreSQL.
6. User logs in and receives signed token.
7. Frontend sends token with protected API requests.
8. Backend saves messages and broadcasts to sender/receiver through WebSocket.

### 6.2 Deployment Architecture
- Frontend: Netlify static deployment from `frontend/out`
- Backend: Railway Go service from `backend`
- Database: Supabase PostgreSQL via transaction pooler
- Email: Brevo API

## 9. Current Limitations

- Attachments are selected and displayed in UI, but full cloud file storage for chat files still needs a dedicated storage bucket integration.
- Admin credentials are hardcoded and should later be moved to environment variables.
- Token signing uses a backend secret; production should set a strong `AUTH_SECRET`.
- Read receipts, typing indicators, message deletion, and group chats are future improvements.

## 10. Future Enhancements

- Add Supabase Storage or S3 for real file uploads.
- Add typing indicators.
- Add message read receipts.
- Add notification system.
- Add group chats.
- Add stronger JWT-based authentication with expiration and refresh tokens.
- Add user privacy settings.
- Add reporting and moderation workflows.
